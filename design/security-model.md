# Security model — container-init, seccomp, and the escape boundary

Audience: engineers and reviewers evaluating the security posture of this fork's
core images (the container-init boot supervisor, the Nix app variant, and the
seccomp profiles). This doc states the design choices, the honest trade-offs
against stock Kasm, and the deployment controls that make the posture sound.

> TL;DR — Two choices in this fork draw scrutiny: (1) enabling Chrome/Electron's
> in-process sandbox via a loosened seccomp profile, and (2) a root PID 1
> (container-init) where stock Kasm runs everything as `kasm-user` (uid 1000).
>
> Choice (2) **is** resolved at the runtime/host boundary (user-namespace
> remapping plus capability dropping): with remapping, this fork's posture is a
> *superset* of stock — same-or-better host isolation, plus setup capability
> stock does not have.
>
> Choice (1) is **not**, and an earlier revision of this doc overstated it
> (§4a). A container seccomp profile cannot be scoped to one binary, so the
> grant reaches every process in the container — including a hostile tenant's
> own code — and uid remapping does not stop a *kernel* exploit, because that
> executes in kernel context where the uid map is irrelevant. The resolution is
> layered, not singular: **seccomp permits the syscall, a MAC profile scopes it
> to the browser, placement decides who shares the kernel** (§5). Until the MAC
> scoping actually lands, the grant is container-wide, and on a shared agent
> host that is a real cost — so the posture is a per-workspace policy (§7), not
> a global default.

---

## 1. Threat models

Security here is not a single scalar; it depends on **who the attacker is**. Two
distinct models, defended by different controls:

- **Model A — "the web is hostile" (attacker = remote content).** The user is
  authenticated/semi-trusted; the danger is a malicious web page or document
  exploiting the browser/renderer. This is the *primary* threat for a browsing
  workspace — isolation of risky content is the whole reason to use one.
- **Model B — "the user is hostile" (attacker = the session user).** The logged-in
  user actively tries to escape the container to the host. The danger is Linux
  kernel attack surface reachable from inside the container.

A control that helps one model can cost the other. Stating which model a
deployment is in is a prerequisite to choosing a posture (§7). Note that the two
models are not always distinct: in any image where the tenant can execute
arbitrary code, Model B's attacker subsumes Model A's, which is what §5 turns on.

## 2. Choice 1 — Chrome/Electron sandbox ON via loosened seccomp

**What stock does:** runs Chrome with `--no-sandbox`, because the default
container seccomp denies the unprivileged `clone/clone3/unshare/setns` that
Chrome's user-namespace sandbox needs.

**What this fork does:** ships two profiles derived from the Moby v25.0.6
default, regenerated by `bin/regen-seccomp.sh`. They are **not** equally
scoped, and the difference is the single most important fact in this section.
Measured as *unconditional* allows (no `includes.caps` gate, no arg filter) for
privileged-adjacent syscalls, relative to the Moby default with
`CAP_SYS_ADMIN` dropped:

| profile | unconditional delta | count | used by |
|---|---|---|---|
| `chrome.json` | `clone`, `clone3`, `unshare`, `setns` | **4** | Chromium/Electron native apps |
| `bwrap.json` | the above **+** `mount`, `umount`, `umount2`, `pivot_root`, `move_mount`, `open_tree`, `fsopen`, `fsconfig`, `fsmount`, `fspick`, `mount_setattr` | **15** | `buildFHSEnv`/bubblewrap apps (OnlyOffice, Steam) |

Under `chrome.json` the mount API stays **blocked**. Those entries survive in
the profile only as `CAP_SYS_ADMIN`-gated rules, and the runtime resolves
cap-gated rules against the container's actual capability set — so with
`CAP_SYS_ADMIN` dropped they are simply absent from the loaded filter, user
namespace or not. Also still blocked: `bpf`, `perf_event_open`, `chroot`
(`CAP_SYS_CHROOT`), `open_by_handle_at`, the module family, `ptrace`.

So what a userns actually re-opens under `chrome.json` is narrower than
"namespaced `CAP_SYS_ADMIN`" implies:

| newly reachable | still blocked |
|---|---|
| root in a new **network** namespace → netlink/netfilter/nf_tables config surface | the whole mount API — old (`mount`/`umount2`) and new (`fsopen`/`fsconfig`/`move_mount`/`open_tree`) |
| the userns/nsproxy/`uid_map` code paths themselves | `pivot_root`, overlayfs mounting |
| per-userns keyrings | `bpf`, `perf_event_open`, module load |

That distinction matters when quoting prior art: the `fs_context` class
(CVE-2022-0185) is **not** reachable under `chrome.json` because it needs
`fsopen`/`fsconfig`; the nf_tables class (CVE-2024-1086) **is**, via
`CLONE_NEWNET`. Verify both against NVD before putting either in a slide — do
not quote them from memory.

`bwrap.json` has no such defence. It hands every process in the container
unprivileged userns *and* the full mount API, which is precisely the
historically most-exploited userns escalation combination. Earlier revisions of
this doc called both profiles "scoped"; only `chrome.json` earns that word.

### Analysis

The claim "Chrome's sandbox hasn't prevented a vulnerability in a long time" is
**not accurate** and should be checked against primary sources (Chrome release
notes, Google Project Zero, the CISA Known-Exploited-Vulnerabilities catalog —
do not rely on remembered CVE numbers). The sandbox is not a bug-catcher; it is
the *containment boundary* for the renderer, where most of Chrome's critical
memory-safety bugs live and are exploited in the wild multiple times per year.
The steady stream of dedicated **"sandbox escape" CVEs** is direct evidence the
sandbox is load-bearing: attackers must spend a *second* bug to get past it.

The trade is **asymmetric**:

| | Defends against | Attack frequency | Cost if removed |
|---|---|---|---|
| Sandbox ON (looser seccomp) | Model A: web content pops the renderer | High — critical renderer bugs are exploited in the wild several times a year | renderer RCE = code execution as the session user, immediately, with no second bug |
| Tight seccomp (userns off) | Model B: the tenant attacks the kernel | Lower — needs a kernel LPE on top of a foothold | one more reachable escalation class (netns/netfilter, §2), and on a shared agent host the blast radius is other customers |

- `--no-sandbox`: a single common renderer bug → **immediate code execution as
  the session user in the container**, no further work. Cheap, frequent.
- Looser seccomp: adds kernel surface (unprivileged userns — a real, named LPE
  risk class, which is why distros ship `kernel.unprivileged_userns_clone=0`).
  But exploiting it requires a kernel LPE, and a hostile authenticated user
  already has a shell + hundreds of syscalls; `--no-sandbox` would not stop them.

Note the same primitive that is the risk (userns) is what *powers* the defense
(the browser sandboxes its renderers with it). Turning the sandbox off to keep
seccomp tight optimizes the wrong layer — *provided* the two can be separated,
which is what §5.2 is for. It is not a surface runtime isolation can own for us:
per §4a, remapping does not stop a kernel exploit.

**The asymmetry holds only while the tenant cannot already execute arbitrary
code in the container.** Where they can — any full desktop image with a terminal
— the two threat models converge on one attacker: whatever a compromised
renderer could do, the tenant can already do directly. The renderer sandbox then
stops buying platform security while the seccomp grant keeps costing kernel
surface, and the trade inverts. §5 handles that case, which is the one that
applies to `tracelabs` and every other desktop workspace.

**Position:** keep the sandbox on for browser/Electron workspaces; keep the
loosening **bounded and per-workspace** — `chrome.json` (no mount) for
Chromium/native, `bwrap.json` (with mount) only for the FHS apps that need it,
never a blanket profile — and pair it with the runtime boundary in §4. Do not
ship `bwrap.json` to untrusted shared-agent tenancy at all until the MAC scoping
in §5 lands. For untrusted-tenant desktops the posture is a policy decision per
workspace (§7), not a property of the base image.

## 3. Choice 2 — root PID 1 (container-init) vs stock's uid-1000

**Stock Kasm** runs the whole container as `kasm-user` (uid 1000): no root.
**This fork** runs container-init as root (uid 0), then drops privilege for
everything it supervises.

### The privilege model (measured, not asserted)

Of the 19 core **service** units in `src/common/kasm-go/units/` (`.service`
files; the `.socket` units are just listeners), only **5 run as root**, and they
are infrastructure/setup, not user-facing:

| Runs as root (uid 0) | Why |
|---|---|
| `kasm-setup.service` | per-session identity (`KASM_OS_USER/UID/GID`), profile seed, ownership/symlinks — needs root |
| `pcscd.service` | smartcard daemon requires root |
| `network-wait.service` | boot ordering helper |
| `recorder-drain` / `recorder-watch` | session-recording plumbing |

Every user-facing service drops to the session user via `User=${KASM_OS_USER}`:
**kasmvnc, window-manager, custom-startup (the actual app/browser), audio in/out,
upload, webcam, gamepad, smartcard, printer, profile-\*, systemd1-shim** (14
units). So the desktop, the browser, and the app the user interacts with all run
as `kasm-user` — identical to stock. Root is confined to PID 1 plus the setup
phase and a few daemons that genuinely require it.

### The real regression is the *mapping*, not the uid

The precise downgrade vs stock is **not** "root inside the container" — it is:

- stock: container-uid-1000 → **host uid 1000** (unprivileged) — an escape lands unprivileged.
- this fork *without userns-remap*: container-uid-0 → **host uid 0** — an escape lands as **host root**.

Name it precisely, because it points at the fix (§4).

### Why root exists here (stock's rootless model has real costs)

Running everything as 1000 buys a clean story by giving up capability:

- **No per-session identity** — `KASM_OS_UID`/`USER` remap needs root.
- **Can't fix mounted-volume ownership at runtime** — a non-root container can't
  `chown` a bind-mounted home/profile to the session user; volumes must be
  pre-owned as 1000 (brittle), and profile-sync restores hit ownership friction.
- **Constrained privileged service setup** — CUPS, pcscd, webcam/audio device
  perms want root or specific caps.
- **Nix activation (this fork)** — `nix-activate` writes `/etc/profile.d`,
  `/usr/share/applications`, runs `ldconfig`, bootstraps `/run/nix-state`, and
  creates `/run/user/<uid>` owned by the session user. As 1000 this degrades to
  user-scoped-only.

Running as root PID 1 that immediately drops privilege is the standard init
pattern (tini, s6, systemd all do it), and is why Kasm itself ships a sysbox
path. The residual root surface is PID 1 + the setup phase; minimize it (§4).

## 4. The unifying control: the runtime/host boundary

Both §2 and §3 concerns collapse to **one** mitigation. Apply it and both stop
being escape paths:

### 4a. User-namespace remapping (or rootless runtime)

With daemon `userns-remap` (or per-container `--userns`, or rootless
docker/podman):

- container-init runs as root **inside the container user namespace** — keeps
  every capability it needs (chown volumes, remap the user, nix-activate).
- container-uid-0 maps to a **high, isolated, unprivileged host uid** (e.g.
  100000) — an escape lands *at least* as unprivileged as stock's 1000, and
  better (stock's host-1000 can collide with a real host account; a remapped
  root cannot).
**What remapping does not do — correcting an earlier claim in this doc.** A
previous revision said an escape *through* the looser seccomp profile "also
lands remapped-unprivileged". That is true only for escapes that work by
*filesystem or namespace* means — a mislabelled bind mount, a writable host
path, a shared namespace — where the attacker's host uid is what decides the
outcome. It is **false for the case the seccomp delta actually opens up**: a
kernel memory-corruption LPE runs in kernel context, so the uid map is
irrelevant and the attacker gets real host root regardless. Remapping raises
the bar (the attacker now needs a kernel bug, not a logic bug); it does not
neutralise the widening. Do not present it as if it does — it is the first
thing a competent reviewer will hit.

Net: with userns-remap, this fork's root PID 1 (§3) is a **strict superset** of
stock — same-or-better host isolation *plus* the setup capabilities stock lacks.
The seccomp delta (§2) needs the separate treatment in §5.

### 4b. sysbox (preferred where available)

`src/ubuntu/install/sysbox/install_systemd.sh` provides the sysbox path: real
systemd, container-init runs as a system unit (`kasm.service`) rather than PID 1.
Sysbox exists precisely to run root/systemd-style workloads in a strongly
isolated container (container-root is safe by design) — it would resolve the
root-PID-1 debate *and* reduce the chrome-seccomp surface at once.

**Sysbox is an either/or, not an additional layer.** Two of its documented
properties are mutually exclusive with the strategy in §5, so this is an
architectural fork that has to be chosen deliberately. From the sysbox user
guide (`docs/user-guide/security.md`, `limitations.md`):

| sysbox property | consequence for us |
|---|---|
| "It's currently not possible to reduce the set of syscalls allowed within a system container (i.e., the Docker `--security-opt seccomp=<profile>` option is not supported)." Sysbox enforces its own fixed ~300-syscall allowlist. | `chrome.json` / `bwrap.json` are **ignored**. The per-workspace seccomp policy in §7 does not exist under sysbox, and the `CLONE_NEWNET` narrowing in §5.3 is impossible. Sysbox's allowlist *does* permit userns creation (DinD/systemd need it), so Chrome sandboxes itself with no profile of ours — but container-wide and unnarrowable. |
| "Sysbox does not yet support AppArmor profiles to apply mandatory access control (MAC) to containers." Requests are ignored. | **§5.2 cannot coexist with sysbox.** Per-binary `userns` scoping is an AppArmor mechanism; under sysbox there is no MAC layer to scope with. |
| "Nested user-namespace: `unshare -U --mount-proc` fails with 'invalid argument'." | Likely breaks bubblewrap, which does exactly this (`--proc /proc` inside a fresh userns) — i.e. the FHS apps (OnlyOffice, Steam) that need `bwrap.json` today. **This is probably the original "sysbox doesn't work with these images" observation.** Untested; one probe settles it, and it needs testing separately for Chrome's zygote. |
| "Host devices exposed to the container … show up with 'nobody:nogroup' ownership. Thus, access to them will fail with 'permission denied' unless the device grants read/write permissions to 'others'." Sysbox names "software that needs access to hardware accelerators" as affected. | GPU workspaces break by default. `/dev/dri` is workable with host-side `o+rw` (at a cost); NVIDIA via `nvidia-container-runtime` stacked under `sysbox-runc` is unverified and should be assumed hostile. |

What sysbox *does* buy: container uid 0→65535 is always mapped to an
unprivileged host range (e.g. 100000+) per container — §4a's benefit,
automatically and without daemon-wide config — plus procfs/sysfs virtualization
and syscall trapping, which lower the value of the userns grant to an attacker
even though the grant is still container-wide. Note it does **not** answer the
objection in §5 by removing the grant; it answers it by making an escape land
nowhere useful. That is a defensible story, and arguably a stronger one than
ours, but it is a different story.

What it does not buy: immunity to a kernel LPE. Sysbox reduces reachable
surface; only a second kernel (gVisor `runsc`, Kata) survives one.

Also note: nothing about sysbox requires systemd. `install_systemd.sh` exists
because upstream Kasm's sysbox images run systemd/dockerd inside; container-init
can be PID 1 under `sysbox-runc` directly. That is the cheapest thing to verify
and it is not what is blocking.

Because §7 previously answered the untrusted-multi-tenant row with "sysbox
required" — a control we have not proven — the boundary for that row is
userns-remap + cap-drop + the MAC scoping in §5 + placement until one of the two
branches is actually validated.

### 4c. Capability + privilege hardening (always)

Independent of the above:

- Drop PID 1 capabilities to the minimal set it needs — roughly `CAP_CHOWN`,
  `CAP_SETUID`, `CAP_SETGID`, `CAP_DAC_OVERRIDE` — and drop the rest.
- `no-new-privileges` on the container.
- read-only rootfs where feasible; tmpfs for writable paths.
- keep the seccomp delta minimal and scoped per workspace (§2).

## 5. The shared-agent-host objection, and what actually answers it

The objection, as raised in review:

> It would be [more secure] if that was what we're doing, and it wasn't a shared
> user environment, but we're not, because we're allowing anything in the
> container to make those syscalls and the agents are full of untrusted users.

"Shared user environment" here means **one agent host, many customers, each in
their own container** — a shared kernel, not a shared container. Two of the
three claims are correct and should be conceded without argument:

1. **The grant is container-wide.** A runtime seccomp profile applies to PID 1
   and every descendant. There is no way to express "only the browser binary may
   call `unshare`" in seccomp. Every process the tenant starts gets the delta.
2. **A userns is a capability grant in disguise.** Creating one confers
   `CAP_SYS_ADMIN` *inside* it, which partly re-grants the very cap-drop that is
   the main thing standing between a tenant and the kernel. The comment in
   `bin/regen-seccomp.sh` — "without weakening any other `CAP_SYS_ADMIN` gates" —
   is true syscall-by-syscall and misleading in effect.

The third claim, that this makes the posture *worse than stock*, is where the
argument is actually decidable, and it turns on one testable premise.

### 5.1 The premise: can the tenant already execute arbitrary code?

The renderer sandbox is worth paying kernel surface for only when the tenant is
**not** already able to run whatever they like in the container. That splits the
image catalogue in two, and it is the reason a single global posture is wrong:

| image class | tenant can exec arbitrary code? | who the real attacker is | what the sandbox buys |
|---|---|---|---|
| single-app browser workspace (no terminal, no file manager, no shell) | no — Chrome offers no syscall-exec primitive | remote web content | **the dominant control.** A renderer bug otherwise means immediate code execution as the session user |
| full desktop (`tracelabs`, XFCE + terminal + 13 tools + 5 browsers) | **yes** | the tenant | session integrity only — no platform-level benefit |

For the desktop case the honest accounting is: the sandbox protects the tenant
from their own browsing, and protects the integrity of a recorded/audited
session; it does **not** protect the platform, because the tenant can already do
everything a compromised renderer could. Meanwhile the seccomp grant costs
platform-level kernel surface. Under a platform-security objective function, on
a shared agent host, **the objection wins for this class of image** — with a
tight profile, `--no-sandbox` is the defensible default, and that is exactly what
stock Kasm ships.

That is the concession. What follows is how to get the sandbox back *without*
paying the cost, because the choice is not actually binary.

### 5.2 The answer: seccomp permits, MAC scopes

Seccomp cannot scope a grant to one executable. AppArmor can. The correct shape
is therefore **not** "loosen seccomp" but:

- **seccomp** allows `clone/clone3/unshare/setns` — necessary, because the
  syscall must reach the kernel at all;
- **AppArmor** grants `userns create` to the *browser* and denies it to
  everything else in the container — sufficient, because on a host with
  `kernel.apparmor_restrict_unprivileged_userns=1` the syscall succeeding is
  gated on the confining profile permitting it.

With both in place, "we're allowing anything in the container to make those
syscalls" becomes true-but-inert: the tenant's shell makes the syscall and gets
`EPERM`, the browser makes it and gets its sandbox. That is a **strict**
improvement over stock — stock gives the tenant no userns *and* no renderer
containment; this gives no tenant userns *and* renderer containment.

**The AppArmor profiles as written today do not do this.** `kasm-desktop:53`,
`kasm-app:35` and `kasm-app-bwrap:40` all carry a bare top-level `userns,`,
which grants namespace creation to every process the profile confines. That
moves the container-wide grant from seccomp to AppArmor; it does not scope it.
Fixing it needs a child profile with an exec transition, and four requirements
that decide whether the scoping is real or theatre:

1. **Attach on a stable, tenant-unwritable path.** Nix store paths are
   content-addressed, so globbing `/nix/store/*-google-chrome-*/**/chrome` means
   re-deriving the glob on every rebuild. Prefer a fixed root-owned launcher
   (the pattern `src/ubuntu/install/xfce/bwrap_dispatch.sh` already establishes)
   with `px -> kasm-browser` on *its* path, which then execs the store binary.
2. **The launcher must exec a fixed target, not `"$@"`.** A launcher that runs
   an arbitrary command under the permissive profile is a one-line bypass:
   `kasm-browser-exec /bin/sh` → tenant shell with `userns`.
3. **The permissive child profile must transition *out* on exec of anything
   that isn't a browser helper.** Otherwise a download → "Open with…" →
   `xdg-open` handler inherits `kasm-browser` and its `userns` grant. This is
   the subtle one and the most likely way a profile that looks right isn't.
4. **Verify the mediation is actually enforced**, not just parsed. Open
   question: whether `deny userns` / omitted `userns` in a *confined* profile is
   enforced independently of the host
   `kernel.apparmor_restrict_unprivileged_userns` sysctl, or only when it is on.
   Test with `apparmor_parser -p` to dump loaded policy plus a negative probe
   (`unshare -Ur true` from a tenant shell must fail) — inspect the kernel's
   view, not the file we wrote.

Caveats to state up front: the profile is **host-loaded** (`bin/load-apparmor.sh`),
so this only works on agents that know about us, and it is Debian/Ubuntu/SUSE
only — the RHEL family needs the equivalent SELinux work, which is not written.
See `design/apparmor-userns-profile.md` for the mount-rule work this depends on;
its phase-2 kill criterion applies here too.

### 5.3 Narrow the seccomp delta further (independent of MAC)

Worth doing regardless, because it shrinks the surface even where AppArmor is
unavailable. The residual under `chrome.json` is essentially
*root-in-a-new-netns*, so:

- **Deny `CLONE_NEWNET` while permitting `CLONE_NEWUSER|CLONE_NEWPID`.** The
  technique is already proven in the baseline: Moby's default gates `clone` with
  a masked-equality arg filter (`value: 0`, mask `2114060288` = `0x7E020000`,
  i.e. allow only when none of the namespace bits are set). Re-add a rule with
  the mask reduced to `CLONE_NEWNET` (`0x40000000`) and the netfilter surface
  goes away. **Unverified:** whether Chrome's zygote tolerates losing network
  isolation for renderers, or hard-fails. Must be measured on a Linux host — it
  cannot be established from a macOS workstation.
- **Deny `NETLINK_NETFILTER` sockets** via an arg filter on `socket()` protocol,
  if the above breaks Chrome. Narrower blast radius, and leaves `NETLINK_ROUTE`
  (which glibc's `getaddrinfo` needs) intact.

### 5.4 Controls that survive a kernel LPE

Nothing in §5.2 or §5.3 stops a kernel memory-corruption bug. Only these do:

- **Placement.** Do not co-schedule untrusted-tenant desktop workspaces with
  other customers on the same agent. This is a backend/scheduling control, not
  an image control, and for the shared-agent-host threat it is the highest-value
  one available — it converts a cross-tenant breach into a single-tenant one.
- **A second kernel.** gVisor (`runsc`) or Kata as the workspace runtime. Then
  the userns grant is a question about the sentry/guest kernel, not the host's,
  and §5.1's whole trade-off dissolves.
- **Cheap host hardening**, all independent of the above:
  `kernel.apparmor_restrict_unprivileged_userns=1` (kept **on** — §5.2 depends
  on it), `vm.unprivileged_userfaultfd=0` (removes a standard heap-grooming
  primitive), `kernel.unprivileged_bpf_disabled=1`, `kernel.dmesg_restrict=1`,
  `no-new-privileges`, and userns-remap per §4a.

### 5.5 Recommended posture for `tracelabs`-class desktops

In priority order, and stated so the interim is not mistaken for the target:

1. **Target:** `chrome.json` + a per-binary-scoped AppArmor profile (§5.2) +
   userns-remap + cap-drop + host sysctls (§5.4). Strictly better than stock.
2. **Interim, until §5.2 is proven:** ship desktops with the **stock-equivalent**
   tight profile and `--no-sandbox`, *or* accept `chrome.json` only where tenancy
   is trusted (single-customer agent, internal use) and say so in the workspace
   registry entry. Do not ship `bwrap.json` to shared agents.
3. **Never:** `bwrap.json` + `apparmor=unconfined` on a shared agent host with
   untrusted tenants. That is the combination the objection describes, and it is
   correct about it.

The generalisation: **make the sandbox/seccomp pair a per-workspace policy field
with the trust assumption recorded next to it**, rather than a property of the
base image. Model A and Model B workspaces have to coexist on the same fleet.

---

## 6. What this fork does NOT change

- The user-facing desktop/browser/app still runs as `kasm-user`, as in stock.
- The seccomp baseline is still the Moby default plus a *bounded, enumerated*
  delta (4 syscalls for `chrome.json`, 15 for `bwrap.json` — §2) — not
  `--privileged`, not seccomp `unconfined`. "Bounded" is not the same as
  "scoped": it is container-wide either way (§5). AppArmor on bwrap workspaces was
  historically run `unconfined` for FHS mount setup; the scoped
  `src/common/apparmor/kasm-app-bwrap` profile now replaces that (re-opens only
  the mount family, keeps every other escape denial). See `docs/apparmor-how-to.md`.
- Capabilities are not broadly added; container-init needs a small set for setup.

## 7. Recommended posture by deployment

Two axes decide a row: can the tenant execute arbitrary code in the container
(§5.1), and do other customers share the kernel?

| Deployment | Model | Chrome sandbox | seccomp | AppArmor | Boundary |
|---|---|---|---|---|---|
| Single-app browser workspace, no shell — dedicated agent *or* shared | A | **ON** | `chrome.json` (4-syscall delta) | `kasm-app` | userns-remap + cap-drop |
| FHS app (OnlyOffice/Steam), trusted tenancy | A | n/a | `bwrap.json` (15) | `kasm-app-bwrap`, **not** `unconfined` | userns-remap + cap-drop |
| Full desktop (`tracelabs`), single-customer agent | A | **ON** | `chrome.json` | `kasm-desktop` | userns-remap + cap-drop |
| **Full desktop, untrusted tenants, shared agent host** | B | ON **only** with per-binary `userns` scoping (§5.2) proven; otherwise **OFF** | scoped MAC → `chrome.json`; no MAC → stock-equivalent tight profile | per-binary-scoped profile is the precondition | userns-remap + cap-drop + host sysctls (§5.4) + **placement**; gVisor/Kata if a kernel LPE is in scope |
| FHS app, untrusted tenants, shared agent host | B | n/a | **do not ship `bwrap.json`** until §5.2 lands | — | as above |
| Air-gapped / low-risk internal | A | ON | `chrome.json` | any | userns-remap + cap-drop |

The single most important line has changed. It is no longer "ensure the runtime
boundary is present" — that was written when sysbox looked available and before
§4a's kernel-LPE caveat was understood. It is now: **decide whether the tenant
can run their own code and whether they share a kernel with other customers.**
If both are yes, the seccomp grant is only defensible once a MAC layer scopes it
per-binary; until then that row runs the stock-equivalent profile, and the
argument for sandboxing is a roadmap item, not a shipped control.

## 8. How to audit

- **Which units run as root:** `grep -L '^User=' src/common/kasm-go/units/*.service`.
- **seccomp delta — reproduce the §2 numbers.** List the unconditional
  privileged-adjacent allows in either profile (expect 4 for `chrome.json`, 15
  for `bwrap.json`):

  ```bash
  jq -r '.syscalls[]
         | select(.action=="SCMP_ACT_ALLOW")
         | select(((.includes // {}) | length) == 0)
         | select(((.args // []) | length) == 0)
         | .names[]' src/common/seccomp/chrome.json \
    | grep -xE 'clone|clone3|unshare|setns|mount|umount2?|pivot_root|move_mount|open_tree|fs(open|config|mount|pick)|mount_setattr|bpf|perf_event_open|chroot' \
    | sort
  ```

  Confirm the mount family is present only as a cap-gated rule in `chrome.json`
  (i.e. absent from the loaded filter once `CAP_SYS_ADMIN` is dropped):

  ```bash
  jq -r '.syscalls[] | select((.includes.caps // []) | index("CAP_SYS_ADMIN")) | .names[]' \
     src/common/seccomp/chrome.json | sort
  ```

  `_patch`/`_regen` fields in the JSON record provenance; regenerate via
  `bin/regen-seccomp.sh`.
- **Is the `userns` grant actually scoped (§5.2)?** From a tenant shell in a
  running workspace, `unshare -Ur true` must **fail**, and the browser must
  still start with its sandbox (`chrome://sandbox` shows the namespace sandbox
  active, or `--enable-logging=stderr` reports no sandbox fallback). Both
  conditions, or the scoping is not working. Cross-check the loaded policy with
  `apparmor_parser -p` rather than trusting the profile source.
- **Effective host uid of container-root:** with userns-remap, inspect
  `/proc/self/uid_map` inside the container (0 should map to a high host uid).
- **Boot privilege trace:** `CONTAINER_INIT_TRACE=1` → `/tmp/container-init-trace.jsonl`
  shows unit start order; cross-reference with the root/user table above.
- **Verify CVE/exploit claims** (e.g. §2) against Chrome release notes, Project
  Zero, and the CISA KEV catalog — not from memory.

## 9. Open follow-ups

Ordered by what unblocks the §7 decision, not by effort.

1. **Per-binary `userns` scoping (§5.2) — the critical path.** Today's profiles
   grant top-level `userns,` (`kasm-desktop:53`, `kasm-app:35`,
   `kasm-app-bwrap:40`), which relocates the container-wide grant rather than
   scoping it. Rework to a child profile with an exec transition off a fixed
   root-owned launcher, meeting all four requirements in §5.2. Everything in the
   untrusted-shared-agent row of §7 depends on this and nothing else.
2. **Measure whether Chrome survives `CLONE_NEWNET` denial (§5.3).** Cheap, and
   it shrinks the residual surface even where AppArmor is unavailable. Needs a
   Linux host — run it on the forge or the GPU test host, not a workstation.
3. **Make the sandbox/seccomp choice a per-workspace policy field** with the
   trust assumption recorded next to it, so Model A and Model B workspaces
   coexist on one fleet. This is the structural fix; the registry `run_config`
   already carries per-app seccomp, so it is mostly a matter of making the
   assumption explicit and reviewable.
4. **Ship a documented `userns-remap` + cap-drop reference config** (daemon and
   per-workspace `run_config`) alongside this doc.
5. **Resolve the sysbox branch** (§4b), in this order — each step is cheap and
   the first failure ends it:
   a. `docker run --runtime=sysbox-runc` a Nix app image with container-init as
      PID 1 (no systemd). Expected to work; confirms the boring part.
   b. `unshare -U --mount-proc true` inside it, then a real bwrap app
      (OnlyOffice). This is the documented nested-userns limitation and the
      likely reason for the original "doesn't work" verdict.
   c. Chrome with no custom seccomp profile: does the zygote get its namespace
      sandbox from sysbox's own allowlist? Check `chrome://sandbox`.
   d. GPU: `/dev/dri` ownership inside the container, and whether
      `nvidia-container-runtime` can stack under `sysbox-runc` at all.
   Record the result either way — including a negative — so no future revision of
   §7 quietly leans on sysbox again. Note (a)–(c) succeeding still forces the
   §4b either/or: sysbox means giving up both the seccomp policy knob and the
   AppArmor scoping, permanently.
6. **Scope the placement control (§5.4)** with the platform team: can untrusted
   desktop workspaces be kept off agents shared with other customers? For the
   shared-agent threat this is worth more than any in-image control.
7. **SELinux equivalent** for the RHEL family — the AppArmor path covers
   Debian/Ubuntu/SUSE only, and the host-load dependency (`bin/load-apparmor.sh`)
   means agents that do not know about us get no scoping at all.
- Nix alpine variant: software-render only today; GPU is future work and must
  feed glibc GL (nix mesa, or host-injected glibc nvidia libs) to glibc apps —
  never the host's musl mesa. See the nix design notes.
