container-init runtime · nix workspaces vs stock Kasm

Faster to a desktop, lighter to run, denser on the box

The same three apps, launched from stock Kasm images (bash boot, Debian packages) and from nix images (the Go container-init PID 1 supervisor, Nix store). Measured standalone on the .140 host. Nix reaches a reachable desktop ~41% sooner, tears down ~40% faster, holds a smaller working set, and packs 321 Chrome sessions per 100 GB vs 214 — a real +50%. The one cost it pays is CPU at boot, and we show that too.

container-init boots concurrently. The Go supervisor resolves the unit dependency graph and starts independent services in parallel with eager socket binds, where the bash chain ran them in sequence. Across all three apps nix is reachable in ~1.6 s vs ~2.7 s. The app's own main process appears at roughly the same moment in both (a parallel boot event, not a later one).

Nix burns ~3–5 extra CPU-seconds per launch. It held steady across warm runs (p95≈median), so it is structural, not cold-cache: container-init fans boot work out across cores in parallel, and Nix's store-based dynamic linking (many /nix/store paths, long RPATHs) is heavier than stock's consolidated /usr/lib. It buys the faster wall-clock start — but at a login storm it is real CPU spend.

The density win is largest for same-app fleets (+50% Chrome, 321 vs 214) and smaller for a mixed set (+13%, 242 vs 215). The binding resident set is dominated by anon, which is private and can't be shared between sessions — so density tracks per-session working set, not cross-app cache sharing. Curves carry ±a few hundred MiB of noise from the active/inactive cache boundary and other host tenants.

Clean shutdown & process footprint

Shutdown = wall time from SIGTERM to container exit (docker stop -t 30). container-init forwards SIGTERM to all children in reverse-dependency order and reaps them; the bash boot leaned on trap handlers and fixed sleeps.

Setup. Host mlserver-ubuntu (192.168.1.140), docker 29 over the Mac linbox context, cgroup v2. Each app launched as a standalone container (docker run, VNC_PW set, --shm-size=1g; nix adds seccomp=chrome.json + apparmor=unconfined) — the Kasm-platform launch path was not used (the nix nginx-reload provision blocker), which also isolates the container from agent/proxy overhead. Both variants ran the software render path; no GPU passthrough. Stock = kasmweb/<app>:1.19.0-rolling-weekly (bash boot). Nix = labs-sandbox/kasm-nix/<app>:nix (container-init PID 1).
Timing. VNC-ready = Mac→LAN TCP connect to the published port (client clock). App-ready = app main process present, measured on the .140 clock from container StartedAt. Both are launch-concurrent boot events. N=5, median reported; p95 tracked ≈ median throughout. Memory read from the container cgroup after a 20 s settle. CPU-to-ready = cpu.stat usage_usec at app-ready. Shutdown = wall time of docker stop -t 30 (SIGTERM→exit). Density ramped 1→8 concurrent, 10 s settle each, fleet = Σ docker stats memory over the run's containers only (host floor guard 20 GB).
Caveats. The box also ran the Kasm stack and other builds, so host MemAvailable is noisy — hence the cgroup-sum metric. "App-ready" is process-present, not window-painted. Single connection; no client-side rendering load simulated. Generated from runs harness · captured 2026-07-09.
