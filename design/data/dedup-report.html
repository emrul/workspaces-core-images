One base, 35 apps — 83% less to store, kilobytes each to add

Every per-app image is crane-appended onto a shared base and shares its Nix-store layers by digest. Pulled cold, the 35 published app images collapse an 82.4 GB naive footprint down to 13.7 GB actually stored. And because that 13.7 GB is essentially the fat store, a content-addressed host that already holds it adds any further app for only its wiring layer — 2.5–4 KB: the multi-hundred-MB Nix payload is already present.

With the fat store: an app is just its wiring

The fat store (nix-store:nix) is published from the same build as the app images, so its Nix-store blobs are byte-identical to theirs. A host that already holds it re-uses those blobs by digest — so pulling any app transfers only that app's tiny wiring layer. Each app's 99.999% — the hundreds of MB of Nix payload — is already there.

▸ Needs a content-addressed image store. The blob re-use lands on Docker ≥ 28 with the containerd snapshotter (or containerd/CRI directly), which keys layers by digest — not the classic overlay2 driver, which keys by chain. The OS/desktop base (shared with kasm-core-ubuntu) is pulled once per host in either case. See docs/docker-setup.md.

Per-app cost

unique layers only — the incremental cost of a cold pull
Sizes are compressed layer blobs read from each image's OCI manifest (docker manifest inspect …:nix), deduplicated by blob digest — so a layer shared across images counts once. Shared base = layers present in all 35 app images (the nix-ubuntu base image plus the common bootstrap store partition). Naive total counts every image at full size. Per-app full ≈ base + its shared + its unique; the ~2 GB floor every app shows is that shared base travelling in each manifest (stored once on disk). With fat store = each app's layers minus the ones the fat store already holds; per-app it is the store-→symlink, appmeta and wiring layers (2.5–4.2 KB). This assumes the fat store was published from the same build (PUBLISH_FAT_STORE=1, so its store blobs are byte-identical — crane compresses a given tar deterministically, base-independently) and a content-addressed client (Docker ≥ 28 containerd snapshotter, or containerd/CRI).
